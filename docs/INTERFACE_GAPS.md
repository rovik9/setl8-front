# Required backend / SDK interfaces

Frontend milestone 2 consumes the additive backend milestone-5 candle contract. The backend-owned declarations were copied byte-for-byte into this frontend; no backend/SDK/vendor/pin or contract-source edit occurred.

1. **Recorded market chart data — supplied and integrated.** Backend milestone 5 supplies authenticated history/candles with exact e18/ns, explicit stream/market/range, deterministic integer OHLC, fixed-cutoff pagination and honest coverage/provenance. Frontend milestone 2 consumes candles in the existing lazy chart, with exact details and conservative bounded plotting coordinates. Actual gateway browser checks cover archived GMX and HL recordings, including three candle pages for HL. This closes the recorded-chart interface gap; it does not establish continuous/current market coverage, retention policy, immutable finality or executable prices. See `MILESTONE_2.md` for separate real versus controlled evidence.
2. **Challenge product catalog and effective rules.** The market catalog exists; challenge account sizes/pricing/phase benefits are not a frontend product-catalog API. Public pricing was therefore not copied from older repositories. Need server-supplied effective product/ruleset data and authoritative target/progress/close eligibility before functional purchase/reset or phase controls. Fee presentation remains 0.4%.
3. **Live account stage.** The user clarified Live follows Phase 5, with 75% profit split, no target, no per-payout limit, unrestricted scaling, minimal rules, negligible spreads, unrestricted news trading and multiple payouts per day. Phases 2–5 have 100% split and 8% per-phase targets. These features are displayed, but current backend admission is disabled and lifecycle is operator-only. Need reviewed Live state/ruleset/eligibility, scaling and payout interfaces. Do not invent a sixth canonical phase enum, close predicate or payout transition. Clarify the precise canonical meaning of “target reaches and balance closes” in the combined handoff; this frontend does not equate a target with an automatic payout.
4. **Canonical trading integration.** M3 supplies unsigned, exact SDK draft preparation and review only; no signature or order POST. M4 now integrates only the Origin-reviewed isolated synthetic prototype on8790; default/live execution remains gated. Need the reviewed combined runtime/SDK candidate, actual per-intent signing/authority integration and enabled admission before functional orders. Historical accepted SDK is 0.1.0-dev.4 / setl8-sdk-dev-v1; historical runtime export is 2c70883ac805f02844530cab5989a98f769ef73e. This read milestone does not depend on or patch pending APIs.
5. **Complete execution/lifecycle outcomes.** Existing activity/intent evidence is incomplete by contract. Full cancel, pending-trigger and SL/TP completion, independent verdicts, signer/submission integration and publication finality require owner-supplied interfaces. Prepared journals/messages are not submitted/finalized claims.
6. **Payout and purchase status reads.** Need bounded versioned request, queue, claim and completed-settlement states before adding user actions. Multiple payouts per day and no per-payout limit are Live features, not a settlement SLA inferred from the current backend.
7. **Account performance history.** Current overview supplies latest persisted state, not balance history or an authoritative return/equity series. Demo paths are illustrative only. Connected views show recorded fields without reconstructing challenge rules or unrealized P&L.
8. **Production environment.** The loopback HTTP cookie/origin policy is intentional local development. Deployment origin/TLS/Secure-cookie and reverse-proxy configuration, real extension/mobile wallets, approved deployed compatibility and independent security review remain outside this milestone.

No request for market depth or an AI assistant is outstanding; the user removed both from scope. No blocker prevents reviewing the completed local frontend.
